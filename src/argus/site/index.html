{{icon:graph:14}} How it works

From page to postmortem.

The loop an experienced on-call engineer runs, as an explicit graph you can read, test and extend. Scroll through one incident.

{{how_graph}}
  1. 01

    Triage in one step

    Golden signals for the alerting service, blast radius from the dependency graph, a severity, and similar past incidents recalled from memory.

    IntakeTriage
  2. 02

    Investigate in parallel

    The commander dispatches up to four analysts with Send. Each is a compiled subgraph (agent, tools, summarize) with its own tool budget, running concurrently with the others.

    DispatchInvestigators ×4
  3. 03

    Diagnose, then doubt it

    The RCA lead ranks hypotheses by how many independent sources support them. The critic checks the gap to the runner-up and loops back for more evidence when it is too small.

    “{{tile_critic_quote}}”
    RCA synthesisCriticneeds evidence ↺
  4. 04

    Plan from runbooks, gate on risk

    Actions come from retrieved runbooks, each with a risk level and an idempotency key. Anything above your policy waits on interrupt(); a rejection with feedback sends the planner back to the drawing board.

    PlanHuman approvalrejected ↺
  5. 05

    Act, then verify

    Approved actions run against the system. The verifier watches the SLOs for several minutes afterwards; if they have not recovered, the next runbook step is planned.

    ExecuteVerifynot recovered ↺
  6. 06

    Write the postmortem

    Timeline, root cause with confidence, evidence, actions taken, key numbers and a customer status update, streamed token by token and downloadable as Markdown.

    Postmortem

{{icon:layers:14}} Engineering

Production patterns, not a notebook.

The graph is small enough to read in one sitting. Everything around it is built the way an on-call tool has to be: durable, observable and safe to retry.

{{code_tabs}}
{{code_panels}}
  • {{icon:database:18}}

    Checkpointed state

    Every step is persisted with the SQLite saver, so an incident survives a crash or a deploy and resumes where it stopped.

  • {{icon:activity:18}}

    Replayable event stream

    The UI follows Server-Sent Events with sequence numbers: reconnect and catch up from any point.

  • {{icon:refresh:18}}

    Idempotent actions

    Each action carries an id; a retried node never applies the same fix twice.

  • {{icon:bell:18}}

    Alertmanager webhook

    Point Prometheus alerts at /api/webhooks/alertmanager and Argus opens the incident.

  • {{icon:lock:18}}

    Locked-down writes

    An optional bearer token guards every endpoint that changes state.

  • {{icon:graph:18}}

    LangGraph Studio ready

    langgraph.json is included: open the same graph in Studio and step through it.
